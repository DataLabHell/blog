open-faraday is a small MCP server that serves spectroscopic reference data and fundamental constants to AI agents — with units, provenance and explicit limits on every response. What that adds over giving an agent generic data access, shown on a single example: the CO₂ contribution to the transmission of air at 15 µm.

github.com/DataLabHell/open-faraday

Curated reference data for spectroscopy already exists: HITRAN's molecular line lists, Kurucz's atomic tables, the CODATA constants — among many others. What fails in practice is the step between that data and an agent's answer. Retrieving a value does not establish its units, physical convention, completeness, database edition or citation. Closing that gap requires no new science — it requires interface constraints, enforced at a protocol boundary rather than left to the agent's discretion. open-faraday addresses this step and only this step: it exposes RADIS and scipy.constants to agents through a fixed response contract.

An API call is not a citation

An agent with a generic HTTP tool can already query HITRAN or any other REST endpoint — and a well-designed domain API can return units, totals, provenance and structured errors. The comparison here is not REST versus MCP; it is generic data access versus a deliberately designed scientific contract. An HTTP request can retrieve a number, but nothing about the retrieval itself establishes which physical convention the number uses, whether the response is complete, which database edition produced it, or how it should be cited. An interface can expose all of this — if it was designed to. open-faraday makes those requirements part of the agent-facing contract. Four failure modes of undisciplined access matter, and all of them are silent:

Failure modeGeneric data access through an agentopen-faraday contract
Naked numbersA float arrives. cm⁻¹ or nm? Vacuum or air? The vacuum/air offset is ~0.1–0.2 nm in the visible — enough to shift a line identification.[1] Every field has a units entry; wavenumbers are labelled cm-1 (vacuum) explicitly.
Silent truncationEndpoints page and cap. An agent that gets 40 lines treats them as all lines — and produces confidently wrong band physics. truncated: true plus total_available on every cut result.
No provenanceWhich database edition? Retrieved when? Cited how? The response doesn't say, so the paper can't either. Source, version, retrieval timestamp, citation and license ride on every response; provenance_report assembles the session bibliography.
Fabrication pressureAn empty or failed response creates an opportunity for the model to fill the gap with a plausible value from prior knowledge. Structured errors only: not_in_database, out_of_validity_range, upstream_unavailable. An error is never shaped like a result.

None of these safeguards is exclusive to MCP — a disciplined REST API could offer every one of them. What open-faraday adds is that they are enforced at a single typed boundary, on every response, rather than depending on each endpoint's design or on the agent's diligence.

One typed boundary — where the discipline lives

In the local configuration used for this session, Claude Code launches open-faraday as a subprocess and speaks the Model Context Protocol with it over stdio. (MCP also supports remote deployments; this post describes the setup actually used.) The client obtains the server's tools — each with a name, a description and a typed parameter schema — and every subsequent call is a structured JSON-RPC message.

Within this data layer the agent therefore sees a deliberately narrow tool surface rather than raw webpages or arbitrary HTTP responses: the declared schemas define the interface. That is what makes the contract enforceable — every answer passes through one typed boundary, so units, provenance, truncation flags and structured errors can be attached there, independent of what the agent does. The CO₂ contribution in one metre of air

The example question: how strongly does the CO₂ in ordinary air absorb thermal infrared near 15 µm? This spectral region is dominated by the ν₂ bending mode of CO₂, a central absorption feature of the greenhouse effect. The calculation isolates CO₂ — the spectrum contains no other constituent of air. The session ran as follows.

Line data. lines_fetch_molecular("CO2", 660, 670) returns the first 10 line records together with truncated: true, total_available: 1361 — 1361 lines of the main isotopologue (the tool's isotope="1" default) in a 10 cm⁻¹ window.[2] The flag is the point: a raw paginated response, taken at face value, could hand the agent those same 10 records with nothing forcing it to notice that 99% of the band had not been retrieved.

Spectrum. spectrum_calculate("CO2", 655–680 cm⁻¹, Tgas=296 K, p=1.01325 bar, x=420 ppm, L=1 m) — a CO₂ mole fraction xCO₂ = 420 × 10⁻⁶. RADIS performs the line-by-line calculation locally, on HITRAN2020 data fetched under HITRAN's own terms.[2] A note on conventions: RADIS calls τ = −ln T "absorbance"; this post calls it optical depth throughout, to avoid confusion with the base-10 absorbance of analytical spectroscopy.

At a CO₂ mole fraction of 420 ppm, the CO₂ alone removes about 98.9% of the radiation at the optical-depth maximum over a one-metre path under these conditions — again, the spectrum contains CO₂ only, not the other constituents of air such as H₂O. The rapidly growing optical depth illustrates why the strongly absorbing central region of the 15 µm CO₂ band becomes opaque over atmospheric-scale paths. In the real atmosphere, where pressure, temperature and composition vary with altitude, that spectral opacity shifts the level from which outgoing thermal radiation can escape — upward near strongly absorbing parts of the band, downward toward the wings. The kilometre calculation shown here deliberately keeps pressure and temperature fixed: it is a homogeneous-gas illustration of that mechanism, not a vertically resolved atmospheric model.

What travelled with the numbers. Each value arrived with units: {"wavenumber": "cm-1 (vacuum)", "values": "dimensionless (0-1)"}, the provenance record "HITRAN line-by-line calculation via RADIS 0.17.1" with database_version: "HITRAN2020" and a retrieval timestamp, and the citations for both the data and the code.[2][1] The 2501-point spectrum was decimated for transport and flagged (truncated: true, total_available: 2501). The two path lengths are also mutually consistent via Beer–Lambert: τ₁ₘ = −ln(0.0115) ≈ 4.47, and 1000 × 4.47 ≈ 4470 ≈ the computed 4466 — the same homogeneous gas, scaled.

Refusal is a feature

The same session then requested the same band at 1500 K, a flame temperature far above HITRAN's intended regime. HITRAN line intensities are referenced to 296 K and can in principle be rescaled to other temperatures; the practical limitation at 1500 K is the completeness of the line list. Transitions and hot bands that are negligible near room temperature become increasingly important at high temperature, while HITRAN applies intensity cut-offs designed primarily for terrestrial atmospheric work — HITEMP is built for that regime. A direct query happily returns a spectrum computed from the incomplete list. open-faraday instead returns: 

{ "ok": false,
  "error": { "code": "out_of_validity_range",
             "message": "HITRAN is recommended for T < ~700 K, requested Tgas=1500.0 K." },
  "notes": ["Consider databank='hitemp' (T < ~2000 K) or 'exomol' for higher temperatures."] }

A structured refusal with a suggested alternative is more useful than a plausible but wrong spectrum. The same principle applies elsewhere in the tool surface: every atomic response carries three coverage caveats (the NIST backend's line_out=1 filter, the absence of energy-level data, and the CPU-only atomic path with its hydrogen default diluent). Limitations are reported rather than worked around.

What this doesn't do

The scope is deliberately narrow, and several limits are worth stating plainly:

  • It finds nothing new. Acceleration, not discovery: RADIS computes the physics, HITRAN/Kurucz/NIST/CODATA own the data, scipy ships the constants. If you write Python yourself, use those directly — or HAPI, HITRAN's own interface.
  • Uncertainty is only as good as the source. Today it is populated for CODATA constants; HITRAN's per-line error codes are not yet passed through.
  • Atomic coverage has real gaps. Lines without transition probabilities and the full ASD level structure are out of scope, and every atomic response says so.
  • Databank validity limits are open-faraday's conservative policy, not fundamental database boundaries. The server refuses HITRAN above ~700 K and HITEMP above ~2000 K as engineering guardrails; the practical range of each database is molecule- and spectral-region-dependent.
  • Incubating. Version 0.1; interfaces may change. No hosted service exists — you run it locally, and no data is bundled or redistributed.

Outlook: the instrument side

The examples above start from a question typed into a chat. The setting we are building toward starts from an instrument. In our laser lab we are extending a microscope into a hyperspectral imaging setup — multi-wavelength illumination, stitched fields of view, deconvolution — where every pixel is not a colour but a spectrum.

Nearly every step in interpreting that kind of data leans on reference data. Checking a wavelength calibration means comparing against known emission lines. Identifying a spectral feature means querying line positions and strengths. Recovering optical properties from spectra means combining measured values with tabulated constants. When agents take over parts of this loop — planning a scan, validating a calibration before a run, flagging a feature worth a second look — each of those steps needs the same discipline shown above: values with units, sources with editions, limits stated rather than hidden.

That is where open-faraday sits: the reference-data layer between the instrument and the agents that work with it, with provenance_report becoming part of each experiment's record. More on the microscope itself once it reaches first light.

The interesting part is not making a language model better at looking up spectral lines. It is making scientific context explicit enough that an agent can use it inside an experiment without silently changing units, assumptions, provenance or validity regimes. Today the question comes from a chat window. Eventually it will come from the instrument itself.

Reproduce it

The session behind this post was run from Claude Code with open-faraday registered as a local MCP server. The following prompt reproduces it:

Using only the open-faraday tools, no values from memory: fetch the CO₂ line list between 660 and 670 cm⁻¹ from HITRAN. Then compute the transmittance of ordinary air (420 ppm CO₂, 296 K, 1.01325 bar) over a 1 m path between 655 and 680 cm⁻¹, and the absorbance of the same air over 1 km. Try the same calculation at 1500 K. Finally, give me the provenance report. Report every value with its units and truncation flags.

The numbers and the figure on this page are the unedited output of the resulting tool calls, with these exact parameters (Python ≥ 3.13, pip install '.[spectroscopy]'): 

# the lines, with honest truncation
lines_fetch_molecular(molecule="CO2", wavenum_min=660, wavenum_max=670, database="hitran")

# the metre of air
spectrum_calculate(molecule="CO2", wavenum_min=655, wavenum_max=680,
                   Tgas=296, pressure_bar=1.01325, mole_fraction=0.00042,
                   path_length_cm=100, quantity="transmittance")

# the kilometre
spectrum_calculate(..., path_length_cm=100000, quantity="absorbance")

# the refusal
spectrum_calculate(..., Tgas=1500, databank="hitran")

# the bibliography
provenance_report()
