What it takes to hand an AI agent a number it can defend — and what breaks when you actually try.

github.com/DataLabHell/open-faraday

TL;DR. open-faraday is a small open-source MCP server exposing spectroscopic reference data (HITRAN, HITEMP, ExoMol, Kurucz, NIST via RADIS) and CODATA constants to AI agents. Every response is a versioned envelope with units, provenance, truncation flags and coverage notes; requests outside validity limits get a structured refusal instead of a plausible number. The one-line position: it refuses to hand an agent a number it cannot defend. The idea worth keeping is scientific context as an executable contract, enforced at runtime; MCP is just the transport. One worked example carries the argument, the CO₂ ν₂ band at 15 µm: 1.13% transmittance at 667.53 cm⁻¹ through one metre of air at 420 ppm, τ ≈ 4487 over a kilometre, every number reproducible tool output. The uncomfortable half of the story is in the second part: holding yourself to that contract surfaces the places where the data supply chain cannot meet it, and most of those turned out to sit upstream, not in our code.

Motivation

AI agents are moving into scientific work, and the question has shifted from whether an agent can call a tool to whether it can be trusted with one. Anyone who has tried knows the failure modes: a physical value supplied from model memory, a unit convention lost between response and answer, a partial result treated as a complete one. None announces itself; the silence is what makes them dangerous in scientific use.

The data itself is not the problem. Curated reference data for spectroscopy already exists: HITRAN's molecular line lists,[1] Kurucz's atomic tables,[2] the CODATA constants,[3] among many others. What fails is the step between that data and an agent's answer: retrieving a value does not establish its units, physical convention, completeness, validity regime, database edition or citation. Closing that gap requires no new science, just interface constraints enforced at a protocol boundary rather than left to the agent's discretion. open-faraday addresses exactly this step, exposing RADIS[4] and scipy.constants[3] through a fixed response contract. The durable idea is not the protocol — it is scientific context as an executable contract: units, conventions, completeness, provenance, validity regimes and explicit failure, travelling with every value. MCP delivers that contract, and the server is deliberately small: a proof of the pattern, not a platform. The second half of this article is about what happened when we took that contract seriously enough to audit ourselves against it.

Scientific context has to cross the interface

Scientific databases already expose excellent programmatic interfaces, and none of what follows requires MCP: typed values and units, truncation metadata, provenance, structured errors and validity checks can all be served by REST, GraphQL, gRPC or a plain Python library, and OpenAPI has offered machine-readable tool discovery for years. The problem we are interested in is different: what information has to cross the boundary together with a scientific result, if an agent is expected to reason with it?

A spectral line is not just a number. Its meaning depends on units, conventions, database edition, isotopologue, the completeness of the query, and the physical regime in which the underlying data is appropriate. The same holds for a calculated spectrum: parameters, assumptions, provenance and validity limits are part of the result.

open-faraday makes these properties an executable scientific contract: the interface requires them, validates them, returns them in a predictable structure, and refuses requests that violate its chosen validity policies. MCP's role is narrower: it gives agents a standardized way to consume that contract. The scientific contract is open-faraday; MCP is the interface it ships today for reaching it. As a single commitment: the interface will not hand an agent a number it cannot defend, and where it cannot defend one, it says so instead of producing it.

There is a difference between a contract a client can read and one it can check, and for a while this was only the first. The envelope was a convention inside a block of text: correct, documented, and impossible to validate without parsing the text and trusting that its shape had not changed. Each tool now declares the envelope as its return type, so the protocol publishes a schema for it and hands back a structured object beside the text. A client validates the contract instead of believing it. Writing the declaration immediately caught a response shape that did not match what we thought we were sending, which is the usual reward for making a claim checkable.

In the setup used here, Claude Code launches open-faraday locally and talks to it over the Model Context Protocol (stdio); the agent discovers five typed tools. The schemas alone are not the contract. What makes it executable is runtime enforcement: validated arguments, mandatory response metadata, checked validity policies, and structured refusals instead of plausible results. Context stops being documentation the agent is expected to remember and becomes part of the behavior of the interface. Use case: The CO₂ contribution in one metre of air

The example question: how strongly does the CO₂ in ordinary air absorb thermal infrared near 15 µm? This spectral region is dominated by the ν₂ bending mode of CO₂, a central absorption feature of the greenhouse effect. The calculation isolates CO₂: the spectrum contains no other constituent of air. The session was run from Claude Code with open-faraday registered as a local MCP server, driven by this prompt:

Using only the open-faraday tools, no values from memory: fetch the CO₂ line list between 660 and 670 cm⁻¹ from HITRAN. Then compute the CO₂ contribution to transmittance in air at a CO₂ mole fraction of 420 ppm (296 K, 1.01325 bar) over a 1 m path between 655 and 680 cm⁻¹, and the optical depth (RADIS quantity "absorbance") of the same homogeneous gas over 1 km. Try the same calculation at 1500 K. Finally, give me the provenance report. Report every value with its units and truncation flags.

Line data. lines_fetch_molecular("CO2", 660, 670) returns the first 40 line records (the default cap) together with truncated: true, total_available: 1361 — 1361 lines of the main isotopologue (the tool's isotope="1" default) in a 10 cm⁻¹ window.[1] The flag is the point: without machine-readable completeness metadata, an agent is free to mistake 40 records for the full line list. The envelope makes that state explicit.

Spectrum. spectrum_calculate("CO2", 655–680 cm⁻¹, Tgas=296 K, p=1.01325 bar, x=420 ppm, L=1 m) — a CO₂ mole fraction xCO₂ = 420 × 10⁻⁶. RADIS performs the line-by-line calculation locally, on HITRAN data fetched under HITRAN's own terms.[1] RADIS calls τ = −ln T "absorbance"; this post calls it optical depth throughout, to avoid confusion with the base-10 absorbance of analytical spectroscopy.

The physics in three equations

The quantity the tool returns is governed by the Beer–Lambert law. Monochromatic radiation of intensity I₀ entering a homogeneous absorbing column of length L leaves it with intensity I, and the transmittance at wavenumber ν is

T(ν) = I(ν) / I₀(ν) = e−τ(ν)

so the optical depth τ counts the e-foldings of attenuation: at τ = 1 the intensity has dropped to 1/e ≈ 37%, at τ = 4.49 to 1.13%. For a uniform gas it grows linearly with the amount of absorber along the path,

τ(ν) = σ(ν) n L,   n = xCO₂ p / (kB Tgas)

where σ(ν) is the monochromatic absorption cross-section per molecule (cm²), n the CO₂ number density (cm⁻³) from the ideal-gas law, and L the path length (cm). The units cancel, so τ is dimensionless, and within this homogeneous-gas model the 1 km path carries exactly 1000 × the optical depth of the 1 m path, which is what makes the two runs mutually checkable. The cross-section itself is what RADIS assembles line by line from the HITRAN records,

σ(ν) = Σi Si(Tgas) φi(ν − νi)

a sum over every transition i in the window: the line intensity Si from the database (rescaled to Tgas via the lower-state energy and partition function), and a normalized line-shape function φi, in practice a Voigt profile combining pressure broadening by air with Doppler broadening. This is why the 1361-line count from the truncation flag matters physically: drop lines from the sum and σ(ν) is simply wrong.

At 667.53 cm⁻¹, near the centre of the ν₂ band, CO₂ at 420 ppm attenuates about 98.9% of incident monochromatic radiation over one metre under these conditions. That number describes one narrow spectral location, not broadband thermal radiation, and CO₂ alone (no H₂O or other constituents of air), with pressure broadening evaluated for CO₂ diluted in air at 1.01325 bar, RADIS' default for molecules. The growing optical depth shows why the strongly absorbing centre of the 15 µm band becomes opaque over atmospheric-scale paths. In the real atmosphere, where pressure, temperature and composition vary with altitude, spectral opacity sets the characteristic altitude from which outgoing thermal radiation emerges: strongly absorbing parts of the band probe higher layers than the less opaque wings. The kilometre run keeps pressure and temperature fixed on purpose: a homogeneous-gas illustration of the mechanism, not a vertically resolved atmospheric model.

What travelled with the numbers. Each value arrived in a versioned envelope (contract: "0.2") with units: {"wavenumber": "cm-1 (vacuum)", "values": "dimensionless (0-1)"}, the provenance record "HITRAN line-by-line calculation via RADIS 0.17.1", a retrieval timestamp, and the citations for both the data and the code.[1][4] The envelope also refuses to overclaim the edition: RADIS requests the latest HITRAN release without recording which one it cached, and the notes say so, pointing to source_download_date instead. The 2501-point spectrum was decimated for transport and flagged (truncated: true, total_available: 2501), and the two path lengths cross-check via Beer–Lambert: τ₁ₘ = −ln(0.01125) ≈ 4.487, and 1000 × 4.487 = 4487, the computed kilometre value exactly.

The envelopes on this page say contract: "0.2" because that is what this session returned, and relabelling them would be the exact thing this article argues against. The contract has since moved to 0.3. Nothing in the molecular or spectrum path changed with it, so these numbers reproduce unaltered; what changed is on the atomic side, and is described below.

Refusal is a feature

The contract also encodes when a result should not be produced. The same session requested the same band at 1500 K, far above HITRAN's intended regime. Line intensities referenced to 296 K can in principle be rescaled; the real limitation at 1500 K is line-list completeness, because hot bands and transitions negligible at room temperature grow important while HITRAN's intensity cut-offs target terrestrial atmospheric work. HITEMP[5] is built for that regime. A physics library still computes what it is asked to compute; open-faraday imposes an application-level policy on top and returns: 

{ "ok": false,
  "error": { "code": "out_of_validity_range",
             "message": "HITRAN is recommended for T < ~700 K, requested Tgas=1500 K." },
  "notes": ["Consider databank='hitemp' (T < ~2000 K) or 'exomol' for higher temperatures."] }

A structured refusal with a suggested alternative beats a plausible but wrong spectrum. The same principle runs through the tool surface: every atomic response carries the coverage caveats of the backend that served it, and only those. A Kurucz response says the A-coefficients are derived from published log gf values and that the list carries no version. A NIST ASD[6] response says the accuracy grade is a graded bound and not a standard uncertainty. Both say that energy levels are not covered as a table, and that the atomic path is CPU-only with broadening partners limited to H, He, H₂ and free electrons; atomic hydrogen is the default and air broadening is unavailable. Shipping the union of both lists would have been less work and would have described neither backend accurately. The ~700 K and ~2000 K ceilings are conservative policy, not fundamental database boundaries; each databank's practical range is molecule- and spectral-region-dependent. Limitations are reported rather than worked around.

Where the contract does not reach

A contract is only worth something if it is also enforced against the party that wrote it. Holding open-faraday to its own promise turned up four places where it could not be kept. One of them was ours and is closed. The other three sit in the layer below, which is the more interesting half of the story.

Uncertainty is available for constants, mostly not for line data. CODATA values arrive with their standard uncertainty and an exactness flag, because scipy.constants carries both. Molecular line data arrives without any, and not because the databases lack it: HITRAN publishes a per-line uncertainty index and a per-parameter reference identifier for every transition,[1] and both are discarded inside the fetcher before open-faraday ever sees the table. Atomic lines are the exception, and only since the rework described below: NIST ASD publishes a letter accuracy grade for every transition probability,[6] and that grade now rides in the response, labelled as what it is. It is a graded bound, not a standard deviation, and the units block says so rather than letting it be read as one. The honest statement of the promise: units always, uncertainty where the source provides it and the retrieval path preserves it.

The HITRAN edition cannot be pinned. RADIS asks HITRAN's server for the current release and records the download date, not which edition came back. For a project whose whole pitch is that a figure can be rebuilt from cited data, an unpinnable edition is a direct hit. The envelope handles it the only honest way, by citing the edition through its retrieval date rather than naming one. Our own documentation did worse for a while: an architecture diagram labelled the source HITRAN2020 while the code deliberately refused to name any edition, and the current release is HITRAN2024.[1] The docs asserted what the code declared unknowable. That is exactly the failure mode the envelope exists to prevent, sitting on our own front page, and it is fixed.

The default atomic source is unversioned and travels over plain HTTP. The Kurucz line lists[2] carry no version, so the provenance record can only say "state at fetch time". They are also fetched over http://, with no transport authentication. That one cannot be fixed by switching the scheme: the host answers on port 443, but its certificate is issued for a different hostname entirely, so a verified TLS connection to the name RADIS uses is not available today (checked 2026-09-16). Nothing distinguishes the real file from an injected one, which is an awkward property for a provenance-first tool. The mitigation available now is to record the exact URL that answered; the real fix is a pinned checksum, and a certificate.

The optional NIST backend downloaded far more than it said. Asking for atomic lines in a 2 nm window did not send a query for that window. It downloaded the complete line table for the species, stored it, registered it as a local database, and applied the window to the file afterwards. A reasonable caching strategy in general, and a poor fit for a government reference compilation served under standard-reference-data terms. It was documented nowhere.

This is the one we could fix ourselves, and the fix was smaller than the problem: the same query, sent with its bounds, through a general-purpose astronomy client that was already installed as a dependency. One request per call, nothing stored, and the client identifies itself honestly on the way out. The interesting part is what came back with it. The bounded path returns the accuracy grade, the observed and the calculated wavelength, the oscillator strength, the relative intensity and the configuration and term label of both levels of every line. It also stops filtering out lines that have no measured transition probability, which ASD lists precisely because they are useful for identification. Doing less work returned more data.

What we sent upstream

The remaining three live in RADIS, the library that does the physics and the retrieval. That is not a complaint. RADIS is an excellent piece of scientific software, it is what makes this project possible, and none of these are bugs in its physics. They are places where a library optimised for computing spectra quietly discards metadata that a provenance-first consumer needs. Building the contract is what made them visible, which is the argument for building contracts.

So the work went where the problem is. Three patches are prepared against RADIS, each with tests, each verified against the installed library rather than against its documentation:

  • Per-line uncertainty and references. The machinery already exists: RADIS' HITRAN database manager can request the uncertainty indices and the reference identifiers, slice them out of the raw record as a fallback, and fail loudly if they go missing. The public fetch function simply never passes the flag, so none of it is reachable. The patch threads the keyword through and warns when a cached database predates it. Worth noting for anyone hitting the same wall: the HITEMP path already returns both columns, because it parses the fixed-width record directly.
  • The ASD accuracy grade. The NIST parser reads the accuracy column, uses it to drop repeated header rows, and then discards it in the final column selection. It is the only per-line uncertainty estimate ASD publishes for a transition probability. The patch keeps it next to the coefficient it qualifies, with an offline test built from a recorded ASD response, since that parser had no test coverage at all.
  • An honest User-Agent. Every database download identified itself as Chrome 91 on Windows, to every host, including the government server hosting the atomic database. It arrived as collateral in an unrelated download fix rather than as a decision. Research data centres size their capacity from their traffic; a browser string makes library traffic indistinguishable from a person clicking a link, so a heavy automated pattern cannot be attributed and the host has no way to reach the project before resorting to a block. The patch sends the library name and version instead. Both strings were checked against all four hosts first and return identical status codes.

This is the part of the story we did not anticipate. The point of a provenance contract is to make an agent's answer defensible. The side effect, once you write the contract down and enforce it, is that it audits the supply chain underneath you, and it turns out the most useful thing a small wrapper can do is send the findings upstream where everyone gets them.

Two shapes for the same contract

The server is one way to deliver a contract, and it is the right one when the agent cannot execute code: a chat client speaks the protocol, the server holds the policy, and an invalid request is refused before anything runs. But a growing share of agents can execute code, and for those, a local server is a process to install and manage in exchange for tool calls that could have been Python.

So a second shape is taking form alongside it: the same policy tables, the same refusals, the same provenance ledger, packaged as a skill that an agent reads and executes directly against RADIS and scipy.constants. Same rules, no process.

The difference between the two is worth stating plainly rather than selling them as equivalent. In the server, the refusal is enforced: a 1500 K HITRAN request cannot get through. In a skill, the refusal is instructed: the agent is told to check the validity gate first, and a sufficiently careless one can skip it. That is a real weakening, and it buys reach. Both are worth having for different clients, which is why the contract lives in tables that both can share rather than in either one's code.

Not the only one any more

When this work started, nothing else exposed spectroscopic line data to agents through a protocol. That changed in September 2026, when an independent HITRAN MCP server appeared and went from nothing to a substantial tool surface in a week. Elsewhere, the largest open scientific agent toolkits now instruct their agents to read CODATA constants straight from scipy.constants — the same mechanism used here.

The honest reading: the barrier to entry is a weekend, and coverage is not a moat. What survives is narrower. It is the envelope, the refusals, the coverage notes and the session bibliography, and whether they are enforced or merely documented. One detail makes the case better than any argument: a widely used physics skill instructs its agent never to hardcode physical constants, then prints its CODATA values labelled with an edition four years older than the one its own dependency ships, and hardcodes a table of particle masses immediately below that instruction. Nobody was careless. Editions drift, and instructions do not notice. A stamped, version-carrying envelope does.

Outlook: the instrument side

All of the above starts from a question typed into a chat. The setting we are building toward starts from an instrument, and this is not speculative for us: the lab is open-faraday's first customer. In our laser lab we are extending a microscope into a hyperspectral imaging setup (multi-wavelength illumination, stitched fields of view, deconvolution) where every pixel is not a colour but a spectrum.

Many of the physically meaningful steps in interpreting that data lean on reference data: wavelength calibration checks against known emission lines, feature identification queries line positions and strengths, optical-property retrieval combines measurements with tabulated constants. When agents take over parts of this loop (planning a scan, validating a calibration, flagging a feature worth a second look), each step needs the discipline shown above: values with units, sources with editions, limits stated rather than hidden.

That is where open-faraday sits: the reference-data layer between the instrument and the agents that work with it, with provenance_report becoming part of each experiment's record. More on the microscope itself once it reaches first light.

The interesting part is not making a language model better at looking up spectral lines. It is making scientific context explicit enough that an agent can use it inside an experiment without silently changing units, assumptions, provenance or validity regimes. Today the question comes from a chat window. Eventually it will come from the instrument itself, and at that point units, provenance, completeness and validity regimes stop being interface niceties and become part of the experimental methodology.

The objective, in the end, is not to make scientific APIs agent-friendly. It is to make scientific assumptions machine-enforceable.

Reproduce it

The prompt in the use-case section reproduces the whole session. The numbers and the figure on this page are the unedited output of the tool calls it triggers, with these exact parameters (Python 3.13–3.14, pip install '.[spectroscopy]'): 

# the lines, with honest truncation
lines_fetch_molecular(molecule="CO2", wavenum_min=660, wavenum_max=670, database="hitran")

# the metre of air
spectrum_calculate(molecule="CO2", wavenum_min=655, wavenum_max=680,
                   Tgas=296, pressure_bar=1.01325, mole_fraction=0.00042,
                   path_length_cm=100, quantity="transmittance", max_points=501)

# the kilometre
spectrum_calculate(..., path_length_cm=100000, quantity="absorbance", max_points=501)

# the refusal
spectrum_calculate(..., Tgas=1500, databank="hitran")

# the bibliography
provenance_report()
